## 定案摘要

1. **本次範圍**：先完成**階段 1–3（純前端改版）**；階段 4（歌曲時長，需改後端）另開下一批。
2. **進階區塊收納**：採用原生 `<details>` 可收合區塊，摘要列顯示精簡狀態（例如 AI 進度 %）；收合 EQ 時暫停頻譜繪製以省電。
3. **畫質資訊整合**：移除頂部畫質標章，保留「畫質上限」下拉選單，並在歌名旁顯示目前播放中的實際畫質（由 `<video>` `videoHeight` 取得，不遮擋 MV 畫面）。
4. **清單操作按鈕**：桌面滑鼠裝置（`@media (hover: hover) and (pointer: fine)`）平常隱藏 `↑ ↓ ×`，滑鼠移入或鍵盤聚焦時以右側漸層浮層淡入（歌名不跳動）；觸控裝置維持常駐顯示。
5. **色彩與模式切換**：沿用紫色為主色、青色專用於「歡唱模式」與「AI 就緒／完成」；導唱／歡唱改為分段按鈕 `[ 導唱 | 歡唱 ]`。

## 現況問題

以 1376×958 視窗截圖觀察：

- 頂部標題已捲出畫面，「AI 伴奏工作室」只露出標題，EQ、人聲削弱、伴奏增益都在畫面下方，唱歌時要捲動才找得到。
- 畫質資訊出現三次且互相矛盾：頂部標章「最高 2K (1440p)」、狀態列「上限 1080p」、下拉選單「1080p 推薦」。
- 狀態列 `#app-status` 夾在搜尋框與播放器之間，不屬於任何區塊。
- 待播清單沒有卡片外框，左右兩欄視覺分量不平衡；每列固定三個按鈕（↑ ↓ ×），壓縮了歌名寬度。
- 「正在播放」只有紫色左框，不夠明顯。
- 導唱／歡唱開關只靠顏色分辨目前模式。
- `#app` 限制在 `max-width: 1200px`，寬螢幕兩側留白過多。

## 階段 1：版面重整

目標：在 950px 高的視窗裡，不用捲動就能看到播放器、模式切換，以及人聲削弱與伴奏增益。

| 項目 | 做法 | 位置 |
|---|---|---|
| 頂部工具列 | 合併成單列：精簡標題 ＋ 搜尋框（移除原本的頂部畫質標章） | `web/index.html` `<header>`、`web/style.css` |
| 放寬版面 | `#app` 的 `max-width` 由 `1200px` 改為 `1440px` | `web/style.css` |
| 清單卡片 | `.playlist-section` 套用與 `.player-section` 一致的卡片樣式，頂端對齊 | `web/style.css` |
| 常用控制上移 | `#quick-controls`（中央人聲削弱）與 `#accompaniment-gain`（伴奏增益）移到模式切換下方，沿用原本的顯示規則：只在歡唱模式顯示，使用 AI 伴奏時隱藏人聲削弱 | `web/index.html`、`web/js/main.js` |
| 可收合區塊 | 「AI 伴奏工作室」與「EQ 與頻譜」改用原生 `<details>`，展開狀態存在 `localStorage`（讀寫皆以 `try/catch` 包住）。AI `<summary>` 顯示精簡狀態／百分比，開始製作時自動展開；EQ 收合時（監聽 `toggle` 並檢查 `eqDetails.open`）暫停 Canvas 60fps 頻譜繪製 | `web/index.html`、`web/js/main.js` |
| 狀態訊息分流 | 搜尋訊息放在搜尋框下方；播放訊息放在播放器標題旁的狀態標籤；成功提示用 Toast；錯誤訊息持續顯示並保留 `aria-live` | `web/js/main.js` `notice()` |

## 階段 2：播放清單

`web/js/main.js` 的 `renderPlaylist()`：

- 每列加上曲目編號（`01`、`02`…）。
- 播放中的歌曲加上「♪ 播放中」標籤與音波動畫；切歌時僅捲動 `#playlist-items` 容器至可見位置（避免帶動外層整頁捲軸）；使用者設定 `prefers-reduced-motion` 時不播動畫。
- 桌面滑鼠裝置（`@media (hover: hover) and (pointer: fine)`）下，`↑ ↓ ×` 平常隱藏，`:hover` 或 `:focus-within` 時以右側漸層浮層搭配 `opacity` 淡入（避免歌名寬度跳動）；按鈕仍保留在 DOM 中，鍵盤與螢幕閱讀器可正常使用；觸控裝置維持常駐顯示。
- 「清空」與匯出／匯入隔開，平常為灰色，滑鼠移上去才變紅。

## 階段 3：控制項與一致性

- **導唱／歡唱**：改為分段按鈕 `[ 導唱 | 歡唱 ]`，使用 `aria-pressed` 與冪等的 `setMode(isSinging)`（點擊已選中模式不會反向切換）；導唱用紫色、歡唱用青色，遠距離也能辨識。
- **製作 AI 伴奏**：可用時使用醒目的主題色；停用時維持灰色，並在按鈕旁顯示原因（取自 `#ai-status`）。
- **畫質**：移除頂部標章；保留控制列的「畫質上限」下拉選單，並在歌名旁顯示目前播放中的實際畫質（於 `<video>` `loadedmetadata` 讀取 `player.videoHeight` 轉為 `2K` / `1080p` / `720p`，不遮擋 MV 字幕與畫面）。
- **音量**：顯示百分比；點喇叭圖示切換靜音，圖示跟著改變。
- **配色**：紫色為主色；青色只用於「歡唱模式」與「就緒／完成」狀態；次要文字的對比至少 4.5:1。

## 階段 4：歌曲時長（已實作）

- ✅ `main.py` `_video_item()` 回傳 `duration`（整數秒；直播、缺值、非數字或超過 24 小時一律為 `null`），搜尋與網址加入皆適用。
- ✅ `web/js/validation.js` 新增 `safeDuration()`／`formatDuration()`，`sanitize()` 保留時長；舊的 `localStorage` 清單與匯入檔沒有時長時仍為有效項目，只是不顯示時長。
- ✅ 清單每列與搜尋結果卡片在歌名下方顯示時長（`3:31`、`1:02:05`），與「♪ 播放中」標籤同一列；滑鼠浮層只蓋右側，不遮住時長。
- ✅ 清單標題顯示「6 首 · 24:10」；部分歌曲（舊清單）缺時長時顯示「24:10+」並以 `title` 說明。
- ⏸ 已完成 AI 伴奏的歌曲加上「AI」標記：仍需逐首查詢 `accompaniment_status`，成本較高，維持另行評估。可行方向是後端新增一次回傳整份清單快取狀態的 RPC。

## 不採納的建議

| 建議 | 原因 |
|---|---|
| ↑↓ 改為 24×18 的垂直堆疊小按鈕 | 18px 高度低於 WCAG 2.5.8 的 24×24 最小點擊範圍，容易誤點 |
| 讓「製作 AI 伴奏」按鈕在停用時也很醒目 | 按鈕變灰是因為停用；醒目的停用按鈕會誤導使用者 |
| 錯誤訊息改用會自動消失的 Toast | 錯誤需要停留到使用者看到為止，並讓螢幕閱讀器讀到 |
| 在影片右上角常駐顯示畫質覆蓋標籤 | 容易遮擋 MV 字幕或右上角台標，改放歌名列旁較不干擾觀看 |

## 實作限制

- `tests/frontend.test.cjs` 目前依賴清單結構：`row.children[0]` 為播放按鈕、`row.children[1]` 為操作按鈕，且斷言 `playBtn.children[0]` 為縮圖、`playBtn.children[1].children[0]` 為歌名。加入曲目編號與「播放中」標籤時，應避免破壞此結構（例如以 CSS `order` 排版或同步調整測試改用語意查找）。
- 分段按鈕 `[ 導唱 | 歡唱 ]` 實作時需同步更新 `tests/frontend.test.cjs` 中對應 `#karaoke-knob` 的測試案例。
- 後端測試指令：`.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py"`。
- 前端測試指令：`.\.tools\deno.exe run --allow-read tests/frontend.test.cjs`（或使用 Node.js 執行 `node tests/frontend.test.cjs`）。
